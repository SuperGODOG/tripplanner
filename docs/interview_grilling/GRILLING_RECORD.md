## 📌 项目通盘概览（应对 HR / 面试官：“请介绍一下项目以及你主要做了哪些？”）

### 1. 一句话项目定位与核心价值
**TripPlanner** 是一个基于 **Python / FastAPI / LangGraph / 高德 MCP / SQLite / DeepSeek** 构建的工业级多日旅行规划 AI Agent 系统。
针对传统大模型在多日长链路规划中极易出现的**“跨天景点重复、路线空间绕远、虚假坐标幻觉、算术超预算”**等痛点，我主导设计并落地了**“确定性算法优先，LLM 最小职责”**的解耦架构，实现了规划结果的 **0 空间幻觉、秒级并发响应与 100% 稳定收敛交付**。

---

### 2. 端到端完整业务流转（4 阶段流水线）
1. **阶段 1：确定性感知与数据层空间分天**
   - 接收用户输入的城市、天数 $N$、偏好与预算；
   - 外部调用高德地图并发检索真实 POI 并自动完成坐标增强；
   - 本地采用 **K-Means++ 空间聚类** 将景点划分为 $K$ 个地理互斥簇（区分市区簇、远郊日与自由日），**在数据层物理消灭跨天重复**；
   - 采用 **Minimax 目标函数** 在城市中心 10km 范围内选出到所有市区景点最大通勤距离最小的酒店。
2. **阶段 2：动态分日扇出与单日闭环（Map 阶段）**
   - 基于 LangGraph **Send API** 根据天数 $N$ 动态并发派发 $N$ 个独立的 `day_node`（实测 $N$ 路并行耗时与单天相当，端到端时延由 20s+ 压降至 3~5s）；
   - 单日内通过 **贪心最近邻 + 2-opt + 营业时间窗硬检查** 纯本地求解最优游览路线；
   - 通过手写轻量 **段落级 BM25** 召回真实小红书风游玩/避坑攻略；
   - `day_agent` **纯推理输出单日文案**（JSON Mode，零工具往返，LLM 失败转本地模板兜底）。
3. **阶段 3：汇聚校验与全链路富化（Reduce 阶段）**
   - 依赖 `Annotated[list, add]` 状态 Reducer 无锁归并多天计划与异常日志；
   - `merge_node` 一次性完成全程统一酒店填充、每日首景点 500m 真实三餐 POI 注入与本地预算核算；
   - 实施全图**纯线性 DAG（彻底删除重试死循环回环）**，遇硬伤记录 `error_log` 透明交付。
4. **阶段 4：持久化与流式交付**
   - 集成 **SqliteSaver** 每步自动快照持久化；通过 **SSE** 实时向前端推送节点进度事件流；API 始终返回 200 OK + 降级面板明细。

### 3. 我在项目中主要负责的核心工作（技术贡献）
- **架构演进与图编排**：设计从“全 LLM 脆弱工作流（v1/v2）”到“确定性计算下沉 + 动态分日并行（v3）”的重构，利用 Send API 显式注入隔离上下文，解决状态竞态与跨 step fan-in 双触发缺陷，Token 消耗降低 60%。
- **空间运筹与算法下沉**：手写落地 K-Means++ 空间聚类、2-opt 消除路径自交叉、Haversine $\times$ 1.4 绕路通行时间估算、Minimax 酒店通勤选址打分。

- **统计信号画像系统**：设计基于 **IQR 四分位距（数值型）** 与 **众数频率比（分类型）** 的双轨异常检测，配合 $\ge 5$ 次冷启动门控，防止单次偶发极端行为污染用户长期画像。

### 第 1 题 · 空间聚类与 POI 稀疏极端边界

#### 1. 问题描述
在 `attraction_node` 中，系统使用手写 K-Means 算法将召回的 POI 聚类分配为 $N$ 天行程。假设用户指定规划 **$N = 5$ 天**，但在该城市召回去重后的**有效市区 POI 数量仅有 3 个**（远少于 $5 \times 2$ 个），同时还有 **1 个距离市中心 85km 的远郊点**（被判定为 `excursion`）。

请回答：
1. 底层聚类算法（`clustering.py`）会如何计算并分配这 3 个市区点与 1 个远郊点？
2. 最终生成的 5 天行程在数据结构（`day_clusters`）和具体展示上分别由哪些天类型（`kind`）构成，`day_index` 排序逻辑是怎样的？
3. 该边界设计在实际业务中是否存在体验/算法缺陷？如果要改进，你的技术方案是什么？

---
#### 2. 用户回答记录
> “第一个问题：根据聚类算法，三个市区是一个簇，一个远郊区是一个簇。至于什么时候触发自由日不是太清楚。
> 第二个问题：kind 分布没看懂，具体排序是根据酒店的 minimax 择远近来排序的。
> 第三个问题：DayNode 先获取景点信息，再根据 Minimax 获取酒店 top1，再把景点、酒店、天气按 day index 完成每天行程。体验不足在于固定工作流灵活度不足，长时间旅游没考虑换酒店。”

---
#### 3. 评析与代码事实纠正 (Critique & Fact Verification)

##### ❌ 存在事实偏差与需纠正的认知：
1. **簇数计算与自由日触发机制（Q1）**：
   - 规则公式：`MIN_PER_DAY = 2`。
   - 计算逻辑（`clustering.py:76-80`）：
     - 远郊点先占 1 天：`remain_days = 5 - 1 = 4`；
     - 市区目标簇数 $k = \min(\text{remain\_days}, \text{len(normal)} // \text{MIN\_PER\_DAY}) = \min(4, 3 // 2) = 1$。
     - 因此 3 个市区点只合成 **1 个常规簇（`normal`）**。
     - **自由日触发点**：当前簇总数（1常规 + 1远郊 = 2）$< 5$ 时，`while len(clusters) < days` 循环自动补齐 **3 个自由活动日（`leisure`）**。
2. **`day_index` 排序机制并非按酒店距离（Q2）**：
   - 排序发生在 `clustering.py:110-121`，**完全不依赖酒店坐标**（因为此时甚至尚未选定酒店）：
     - **市区簇（`normal`）**：按簇内 POI 的**平均经度**升序排列（近似地理东西向移动），分配为前置天数（`day_index = 0`）；
     - **远郊日（`excursion`）**：排在市区簇之后（`day_index = 1`）；
     - **自由日（`leisure`）**：排在最后补齐剩余天数（`day_index = 2, 3, 4`）。
3. **时序与 `day_node` 职责边界（Q3）**：
   - **酒店选址不在 `day_node` 内**：`hotel_node` 是在图拓扑的前置阶段（`_fan_out` 之前）一次性通过 Minimax 选定，作为 `hotel_selected` 上下文注入到 Send payload 中。
   - **`day_node` 对不同 `kind` 的执行分支**：
     - `normal` / `excursion`：执行本地路径求解（`route_solver.py`）+ BM25 攻略检索 + 单天文案 LLM 调用；
     - `leisure`：在 `nodes.py:614-619` **直接短路返回固定文案**，不消耗算力、不调用 LLM。
4. **业务缺陷与改进方案**：
   - **业务痛点**：5 天行程出现多达 3 天“自由活动日”，规划极度空洞。
   - **改进方案**：在 `attraction_node` 检测到候选数量不足时，引入**自适应泛化召回**（扩大搜索半径至 30km 或自动扩充“公园/步行街/夜市”等宽泛关键词），而非过早放弃并退化为自由日。

### 第 2 题 · 拓扑并发与数据隔离边界

#### 1. 问题描述
在 v3 架构中，规划天数通过 LangGraph 的 `Send("day_node", payload)` 动态并发扇出（Fan-out），最后由 `merge_node` 汇聚（Fan-in）。

请回答：
1. **数据隔离边界**：为什么 `_fan_out` 必须将 `city`、`weather_data`、`hotel_selected`、`user_profile` 显式写入 payload，而不是让 `day_node` 直接从全局 State 中读取？LangGraph 的 `Send` 机制在底层是如何处理分支状态的？
2. **并发冲突与状态合并**：当 $N$ 个 `day_node` 同时并行执行并产出结果时，为什么不会发生多线程写入状态的“脏写/覆盖（Race Condition）”？系统在 `State` 声明中使用了什么机制来保证数据安全归并？
3. **聚合节点触发机制**：在你的测试与代码实现中，多路 `day_node` 并行汇聚到 `merge_node` 时，`merge_node` 会被触发执行几次？如何从图拓扑设计上避免多入边重复触发？

---
#### 2. 用户回答记录
> “第一个问题：主要是防止上下文爆炸吧。因为并发节点只需要城市、天气、酒店、画像。Send 机制通过并发多个 agent，每个读初始 payload，根据划分的不同 payload 执行文案，然后通过 reducer 合并。在这个过程中可能发生死锁，于是建立全局单例池将叶子任务作为最小单元防止死锁或覆盖。
> 第二个问题：采用将叶子任务作为原子化操作，哪怕同时返回也会排队，用的是 Python 后台 first-in-first-out 机制。
> 第三个问题：MergeNode 只会触发一次，因为在 DayNode 并行时其他叶子节点已在队列中。具体是等全部处理完汇聚到一起，然后走 reducer 汇合成一块。”

---
#### 3. 评析与代码事实纠正 (Critique & Fact Verification)

##### ❌ 存在事实偏差与混淆的认知：
1. **Send 显式注入的底层原因（Q1）**：
   - **混淆点**：将“防止上下文膨胀”与“LangGraph Send 物理状态隔离”混淆；同时将“底层高德 MCP 全局线程池”与“图编排 Send 机制”混为一谈。
   - **代码事实**：LangGraph 的 `Send("day_node", payload)` 在底层设计中具有**严格的分支状态隔离**。子分支 `day_node` 接收到的 `state` **仅仅是 payload 字典本身，不会自动继承父图的全局 State**。如果不显式写入 `city` 或 `hotel_selected`，子分支内部直接读不到数据（引发 `KeyError` 或空数据）。
2. **并发无覆盖的真实机制（Q2）**：
   - **混淆点**：误认为是“Python 后台 FIFO 队列排队写入”。
   - **代码事实**：并发无覆盖的根本原因是 **LangGraph 状态机通道的 Reducer 声明**（`state.py:43, 65`）：
     - `plan_days: Annotated[list, operator.add]`
     - `error_log: Annotated[list, operator.add]`
     - 在 LangGraph 的 Pregel 执行引擎中，同一个 Superstep 内并行的各个 `day_node` 产出的增量字典，在步末通过 `operator.add`（即 `list.extend`）进行**原子状态规约（State Reduction）**，无需应用层加锁或队列排队。
3. **`merge_node` 触发一次的本质原因（Q3）**：
   - 在 LangGraph Pregel 模型中，由同一个 `_fan_out` 步骤派发的 $N$ 个 Send 分支属于**同一个执行 Superstep**。引擎会等待该步内所有分支全部执行完毕、完成 Reducer 状态合并后，才推进到下游节点 `merge_node`。
   - 因为所有分支共享同一条终点边 `day_node -> merge_node`，引擎将其收敛为单次执行，实测确认只触发 1 次。

### 第 3 题 · 长期记忆统计信号与异常画像边界

#### 1. 问题描述
用户的长期偏好记忆系统（`MemoryManager` + SQLite 租户存储）放弃了传统的简单 CRUD 存取，采用了“双轨异常检测 + 渐进画像”机制。

假设用户 Alex 历史上有 5 次旅行记录，行为高度一致：
- 酒店价格：5 次均为 300~500 元（经济型快捷酒店）；
- 饮食标签：5 次均为“饮食:不吃辣”。

第 6 次规划时，Alex 突然陪客户出差，输入了：
- 酒店预算：“价格:1800-2200”；
- 饮食偏好：“饮食:爱吃辣”。

请回答：
1. **双轨异常检测算法细节**：对于新产生的“价格”和“饮食”标签，底层 `_compute_outlier_penalty` 是如何分别进行异常判定的？IQR 的判定公式与分类型的众数频率比公式具体是什么？
#### 2. 用户回答记录
> “第一个问题：双轨异常检测这一块忘了是哪双轨了，只记得有个方差计算，超出方差就降权。
> 第二个问题：新记录也会写入 SQLite，但是权重降低（outlier_penalty）。由于有缓冲机制，异常情况不会突然改变现行主流画像。
> 第三个问题：如果用户持续输入豪华型，随着数据增加阈值会扩大，最终实现偏好修改。冷启动设定 5 次是因为统计判定公式需要积累一定样本才具有统计意义，避免前一两次产生极度不准确的误判。”

---
#### 3. 评析与代码事实纠正 (Critique & Fact Verification)

##### 💡 概念澄清与核心机理：
1. **何为“双轨”（Q1 - 记忆系统的两类数据通道）**：
   - **轨道 1：数值型字段（价格/预算/距离）走 IQR（四分位距法）**
     - 代码位置：`manager.py:252-284`；
     - 为什么不用均值/方差？因为**均值和方差极易被极端值拉偏**（1 个 2000 会直接把均值拉高 300）；而 **四分位数（$Q_1, Q_3$）与中位数（Median）** 对极端离群点有极强的鲁棒性；
     - 判定区间：$\text{Price} < Q_1 - 2 \times IQR$ 或 $\text{Price} > Q_3 + 2 \times IQR$。
   - **轨道 2：分类型字段（饮食/交通/住宿/节奏）走 众数频率比**
     - 代码位置：`manager.py:285-330`；
     - 判定逻辑：新标签历史频次 $< \text{同维度众数频次} \times 0.3$ 时判定为异常。
2. **权重打标与画像防突变（Q2）**：
   - 异常记录**依然正常入库**，但被赋予 `outlier_penalty = 0.3`（权重打 3 折）；
   - 在生成画像 `build_profile` 时，价格区间取**所有历史价格的中位数**：5 个 400 元 + 1 个 2000 元，其中位数依然是 400 元，因此 Alex 的画像**完全不受单次 2000 元影响，稳定保持为经济型**。
3. **真实偏好平滑演进与冷启动（Q3）**：
   - **平滑演进**：当用户连续多次产生豪华型消费时，一方面新记录的高频次带来 `frequency_boost` 上升，且**时间衰减因子（`time_decay`）**赋予最新记录更高权重；另一方面价格列表的中位数逐步右移，画像自然、平滑地过渡到豪华型。
   - **冷启动门控（$\ge 5$ 次）**：在小样本（1~2 次）下统计学方差无意义，过早生成画像容易产生严重的刻板印象。

### 第 4 题 · 全图无回环与多层级容灾降级边界

#### 1. 问题描述
在早期 v2 架构中，系统通过 `retry_planner` 条件边进行 LLM 生成硬伤重试；而在 v3 架构中，全图被重构为**纯线性 DAG（无任何回环）**。

假设某次规划中同时发生了以下 3 级异常：
1. **外部工具层**：高德天气接口出现网络抖动，底层 `run_mcp` 超过 10s 未返回；
2. **单日生成层**：Day 2 的 `day_node` 调用的 LLM 连续 3 次返回非法代码片段（JSON 解析失败）；
3. **汇聚校验层**：`merge_node` 本地计算总预算时，发现门票+酒店总花费超出用户输入预算上限（出现校验硬伤）。

请回答：

#### 3. 评析与代码事实纠正 (Critique & Fact Verification)

##### 🛠️ 核心机制系统复习与代码事实：
1. **删除 `retry_planner` 回环的技术决策（Q1）**：
   - **v2 的痛点**：当大模型整单生成 5 天出现硬伤时，通过条件边回环塞给大模型重试。大模型经常无法准确理解硬伤，导致重试 3 次均告失败，徒增 15~20s 延迟并最终超时崩溃。

   - **若偶发硬伤的处理**：`merge_node`（`nodes.py:813-815`）发现硬伤时**绝不回环**，仅记录 `error_log: "校验发现硬伤但本地链路无法重试，已按当前结果交付"`，直接交付降级方案。
2. **三处故障的真实逐级降级链条（Q2）**：
   - **故障 1（天气超时）**：底层 `run_mcp` 10s 触发 `FutTimeout` 截断，`_validate` 触发**天气降级文案**（`"天气数据暂不可用，建议春秋季带外套..."`），`merge_node` 写入 `error_log`；
   - **故障 2（Day 2 文案 LLM 失败 3 次）**：`_run_agent_with_retry` 指数退避重试（1s $\to$ 2s $\to$ 4s）仍失败后，`day_node` 捕获异常，**立即启用本地静态模板兜底**（`nodes.py:675-715`），直接拼接真实 POI 名称生成保底文案，标记 `status="llm_fallback"`，**不等待、不阻塞其他天，全流程继续推进**；
   - **故障 3（Merge 预算硬伤）**：校验记录硬伤日志，并将全局方案的 `status` 标记为 `"degraded"`（正常为 `"success"`，全无计划为 `"fallback"`）。
3. **`error_log` 累积机制与透明交付价值（Q3）**：

#### 3. 评析与代码事实纠正 (Critique & Fact Verification)

##### 🛠️ 核心机制系统复习与代码事实：

1. **本地路径求解与 2-opt（Q1）**：
   - **为什么不调高德路线规划 API**：在一个包含 $M$ 个景点的簇内排 TSP 路径，构建两两距离矩阵需要调用 $O(M^2)$ 次高德 API。5 天行程需要调用数十次外部接口，**网络时延从 0.1ms 飙升至数秒，且会瞬间打爆 QPS 限额**。采用 Haversine 直线距离 $\times 1.4$ 城市绕路系数，0 成本、0.1ms 即可获得高精度的通行耗时。
   - **2-opt 的核心作用**：经典的 TSP 局部搜索算法，核心作用是**消除路径自交叉（Crossing Edges）**（例如折返跑：$A \to C \to B \to D$ 优化为 $A \to B \to C \to D$），使日内游览总里程最短。
   - **时间窗超限的实际降级**（`nodes.py:630-636`）：如果一天内景点排完后超出营业时间，系统**绝不擅自删除景点**，而是**触发软伤降级**：保留聚类 POI 顺序但去掉具体时间戳标注，把取舍权留给用户。

2. **BM25 攻略 RAG 的 Query 意图词增强（Q2）**：
   - **为什么 Query 是 `景点名 + 玩法`（`guide_rag.py:121-124`）**：
     - **真实痛点**：精选攻略的正文段落通常**不重复出现景点名称**（例如故宫玩法段落，正文第一句是“从午门进，直奔太和殿，切忌走东华门...”，段落中根本没有“故宫”二字）；
     - 若只用纯景点名“故宫”去算 BM25，会出现**大面积词频为零（TF=0）无法召回**的尴尬情况；
     - **增强技巧**：将 Query 扩充为 `故宫 + 玩法`，意图词“玩法”能够精准匹配段落前缀标签【玩法】，从而把最核心的游览避坑段落打高分召回。

3. **测试基线捕获的 5 项隐蔽缺陷机理（Q3）**：
   - **隐蔽缺陷 1：LangGraph fan-in 跨 step 双触发**
     - *机理*：在早期版本中，`attraction` 和 `memory` 两个分支都连到 `planner` 节点，因为它们在不同的 Superstep 结束，导致下游的 `planner` 节点被**重复触发执行了 2 次**（每请求跑了 2 遍 LLM）；
     - *修复*：v3 通过 Send API 动态派发并在同一个 Superstep 汇聚，确保 `merge_node` 只触发 1 次。
   - **隐蔽缺陷 2：高德 POI 经纬度缺失**
     - *机理*：高德 `maps_text_search` 返回的 POI 很多不带 `location` 字段，导致候选点在进入 K-Means 时全部因缺坐标被丢弃，引发“未找到任何景点”崩溃；
     - *修复*：在 `AmapToolWrapper` 内部引入 `_enrich_pois_with_coords`，并发调用 `maps_geo` 强制按地址反查补齐坐标。
   - **隐蔽缺陷 3：用户画像 None 击穿**
     - *机理*：新用户 `user_profile` 中某些字段（如 `accommodation` / `budget_tier`）为 `None`，在后续节点格式化时直接引发 `KeyError` 或 `TypeError`；
     - *修复*：在 State 提取层增加健壮的缺省字典兜底。
   - **隐蔽缺陷 4：LLM 幻觉坐标（偏差 1300km）**
     - *机理*：早期让 LLM 生成坐标，LLM 把北京景点的经纬度编造成了西安的坐标（偏差 1300km）；
     - *修复*：全面推行“确定性优先”，LLM 彻底不输出坐标，坐标全程由高德真实数据结构化流转。

## 🛡️ 第三阶段 · 系统韧性、高并发治理与质量工程深度复盘

### 1. 全局单例线程池（`max_workers=10`）与死锁防御
- **为什么多个偏好并发会导致 QPS 被击穿？（乘积形式并发）**：
  - 用户传入 5 个偏好（如 `["历史", "美食", "自然", "夜市", "亲子"]`）；
  - `attraction_node` 对 5 个偏好发起 5 路并发周边检索；每个检索返回 10 个 POI，Wrapper 内部又需对这 10 个 POI 并发调用 `maps_geo` 补齐经纬度（10 路并发）；
  - 嵌套并发量瞬间达到：$5 \text{ (偏好)} \times 10 \text{ (POI 坐标)} = 50 \text{ 路并发请求}$！
  - 高德个人免费 Key 的并发上限仅为 20~25 QPS，瞬间 50 并发会直接触发 HTTP 429 / 限流熔断，导致全图崩溃。
- **为什么全局单例池只接“叶子任务”就能彻底防死锁？**：
  - **死锁机理（线程池饥饿死锁 Thread Starvation Deadlock）**：如果把“外层父任务（5 个偏好的搜索编排）”也放进这个 `max_workers=10` 的线程池，当 10 个父任务占满全部 10 个工作线程时，父任务需要调用内层的 `maps_geo` 子任务才能完成。但此时线程池已被父任务占满，子任务只能在任务队列中排队等待空闲线程，而父任务又在占用线程同步等待子任务返回 $\to$ **父等子完成，子等父释放线程，形成 100% 永久死锁！**
  - **防死锁铁律（Leaf-Only Rule）**：外层父任务留在独立的业务线程或协程中，全局单例池**只接收不可分割的原子级 `mcp.run` 叶子任务（Leaf Tasks）**。叶子任务内部绝不产生新的子任务，执行完立即释放线程，因此绝对不会发生嵌套死锁。

### 2. LLM 指数退避（Exponential Backoff）与随机抖动（Jitter）防惊群
- **指数退避时间序列**：
  - 重试公式：$\text{Delay} = \text{base\_delay} \times 2^i + \text{random}(0, 0.5)$ 秒。
  - 第 1 次重试：$1 \times 2^0 \approx 1\text{s} + \text{jitter}$；
  - 第 2 次重试：$1 \times 2^1 \approx 2\text{s} + \text{jitter}$；
  - 第 3 次重试：$1 \times 2^2 \approx 4\text{s} + \text{jitter}$。
- **为什么必须加入随机抖动（Jitter）？（防惊群效应 Thundering Herd）**：
  - 在 v3 架构中，系统通过 Send API 同时并发派发了 5 个 `day_node`；
  - 假设 LLM API 在某一瞬间出现网络抖动，5 个 Day Agent **同时失败**；
  - **如果不加 Jitter**：5 个 Agent 会在**完全相同的时刻（精准 1.000 秒后）同时发起第 1 次重试**，产生集中尖峰脉冲再度打爆 API 限流；
  - **加入 Jitter（0~0.5s 随机浮动）**：5 个 Agent 的重试时间被随机错开（如 1.08s、1.23s、1.45s、1.12s、1.39s），把脉冲尖峰抚平，大幅提升重试成功率。

### 3. SSE 断开取消与连接池安全管理
- **客户端中途关闭或断网抛出什么异常？**
  - FastAPI / Starlette 会在 ASGI 传输层捕获客户端连接断开，向协程抛出 **`asyncio.CancelledError`**。
- **后端如何终止后台图任务？**：
  - 在 `app/api/trip.py:127, 166` 中，维护了一个线程安全事件 `cancel_event = threading.Event()`；
  - 捕获到 `CancelledError` 时，立即触发 `cancel_event.set()`，并在后台线程执行中拦截后续节点，中止无意义的计算与 Token 浪费。
- **为什么在 `finally: conn.close()` 中显式关闭？**：
  - `open_trip_graph()` 每次为当前请求独享建立一个 SQLite 连接。如果不显式关闭，在高并发请求或用户频繁中断时，大量未关闭的连接会堆积，耗尽系统的文件描述符（fd 泄漏导致 `Too many open files` 崩溃）。

### 4. 离线测试捕获的 5 大隐蔽缺陷详解
编写的 60 个单元测试通过 **Fake 依赖注入（FakeAmapWrapper / FakeRepository / FakePlanner）**，实现**全脱机、零网络依赖、零 Token 消耗、0.8 秒全量执行**。曾精准捕获并修复了以下 5 个隐蔽缺陷：

1. **LangGraph fan-in 跨 step 双触发缺陷**：
   - *机理*：早期 `attraction`（网络长任务，Step 2 结束）与 `memory`（本地短任务，Step 1 结束）汇聚到 `planner`，由于在不同的 Superstep 结束，导致下游 `planner` 节点**每请求被重复执行了 2 遍**（浪费双倍 Token 并产生状态混乱）。
   - *修复*：v3 改为 Send API 动态扇出并在同一 Superstep 统一汇聚，保证 `merge_node` 只触发 1 次。
2. **高德 POI 经纬度缺失缺陷**：
   - *机理*：高德 `maps_text_search` 返回的 POI 很多不带 `location` 坐标，进入 K-Means 时全部因缺坐标被丢弃，引发“未检索到任何景点”崩溃。
   - *修复*：Wrapper 内部引入 `_enrich_pois_with_coords` 自动级联 `maps_geo` 补齐坐标。
3. **用户画像 None 击穿缺陷**：
   - *机理*：新用户画像中某些字段为 `None`，在后续节点格式化时直接引发 `KeyError`。
   - *修复*：在 State 提取层增加缺省字典兜底。
