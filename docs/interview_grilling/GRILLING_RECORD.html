TripPlanner 深度面试与业务边界考查全景

涵盖端到端架构哲学、空间运筹算法（K-Means/2-opt/Minimax）、LangGraph Send 并发与状态规约、双轨统计记忆与 5 级容灾降级体系。

1. 一句话定位与核心价值

TripPlanner 是一个基于 Python / FastAPI / LangGraph / 高德 MCP / SQLite / DeepSeek 构建的工业级多日旅行规划 AI Agent 系统。针对传统大模型在长链路规划中极易出现的“跨天景点重复、路线空间绕远、虚假坐标幻觉、算术超预算”等痛点，主导设计并落地了“确定性算法优先，LLM 最小职责”的解耦架构，实现了规划结果的 0 空间幻觉、秒级并发响应与 100% 稳定收敛交付。

2. 端到端完整业务流水线（4 阶段）
阶段 1
确定性感知与空间分天
高德多偏好检索 + 坐标增强；K-Means++ 空间聚类保证跨天互斥；Minimax 目标函数选定中央酒店。
阶段 2
动态分日扇出 (Map)
LangGraph Send API 派发 N 路并行；贪心+2-opt+时间窗排路线；手写 BM25 召回真实玩法；LLM 纯生成文案。
阶段 3
汇聚校验与富化 (Reduce)
Annotated Reducer 无锁合并；填充酒店与首景点三餐 POI；本地算预算；纯线性 DAG 无回环，硬伤降级交付。
阶段 4
持久化与流式交付
SqliteSaver 每步快照；SSE 实时推送节点进度事件；API 始终返回 200 OK + 降级面板明细。
3. 我在项目中主要负责的核心技术工作
  • 架构演进与图编排：设计从全 LLM 脆弱流向“确定性计算下沉 + 动态分日并行”重构，利用 Send API 显式注入隔离上下文，解决状态竞态与跨 step fan-in 双触发缺陷，Token 消耗骤减 60%，耗时由 20s+ 压缩至 3~5s。
  • 空间运筹与算法下沉：手写落地 K-Means++ 空间聚类、2-opt 消除路径自交叉、Haversine × 1.4 绕路通行估算、Minimax 酒店通勤选址打分。
  • 轻量 RAG 与多源知识协同：放弃沉重向量库，针对确定性景点实体手写 Bigram BM25 检索算法与 Query 意图词增强（景点+玩法），实现攻略覆盖率 83% 且引用可溯源。
  • 高并发治理与死锁防御：针对外层多偏好与内层坐标增强产生的 25+ 嵌套并发，构建单例全局 MCP 线程池（限流 ≤ 10），确立“全局池仅提交叶子任务”铁律，杜绝 QPS 打爆与线程池饥饿死锁；配合 LRU 缓存加速。
  • 统计信号画像系统：设计基于 IQR 四分位距（数值型） 与 众数频率比（分类型） 的双轨异常检测，配合 ≥ 5 次冷启动门控，防止单次偶发极端行为污染用户长期画像。
  • 质量工程与高可用体系：编写 60 个无网络、无真实 LLM 的离线单元测试（全 Fake 注入），建立 5 级渐进式容灾降级网与 error_log 累积机制，保证极端异常下服务零崩溃。

第 1 题 · 空间聚类与 POI 稀疏极端边界

K-Means++ 聚类 · 自由日触发 · 边界降级
场景设定：用户规划 N = 5 天，但该城市召回去重后有效市区 POI 仅有 3 个（少于 5×2 个），同时有 1 个距离市中心 85km 的远郊点（判定为 excursion）。
  1. 底层聚类算法（clustering.py）中，目标簇数 $k$ 的计算公式是什么？这 3 个市区点与 1 个远郊点最终如何划分？
  2. 最终生成的 5 天行程在 day_clusters 中的 kind 分布及 day_index 排序规则是怎样的？
  3. 该设计在业务体验上是否存在不足，如何改进？
“根据聚类算法，三个市区是一个簇，一个远郊区是一个簇。至于什么时候触发自由日不是太清楚。kind 分布没看懂，具体排序是根据酒店的 minimax 择远近来排序的。DayNode 先获取景点，再根据 Minimax 获取酒店 top1，再把景点、酒店、天气按 day index 完成每天行程。体验不足在于固定工作流灵活度不足。”
💡 深度评析与代码事实标准答案
  • 簇数计算与自由日触发机制（clustering.py:76-80）： 规则定义 MIN_PER_DAY = 2。远郊点先占 1 天（remain_days = 5 - 1 = 4），市区目标簇数 $k = \min(4, 3 // 2) = 1$。因此 3 个市区点合并为 1 个 normal 市区簇。当前簇总数（1 normal + 1 excursion = 2）< 5，while len(clusters) < days 循环自动补齐 3 个自由活动日（leisure）。
  • day_index 排序机制并非按酒店（clustering.py:110-121）： 聚类时酒店尚未选定。排序规则为：
    1. 市区簇（normal）：按簇内 POI 的平均经度升序排列（近似东西向移动），分配为 day_index = 0；
    2. 远郊日（excursion）：排在市区簇之后，分配为 day_index = 1；
    3. 自由日（leisure）：排在最后补齐剩余天数，分配为 day_index = 2, 3, 4。
  • 时序与短路机制： 酒店选址在 hotel_node 阶段一次性选定。day_node 遇到 leisure 时，在 nodes.py:614-619 直接短路返回固定休闲文案，零 LLM 消耗。
  • 业务缺陷与改进： 5 天行程出现 3 天自由日过于空洞。应在 attraction_node 召回不足时触发自适应泛化召回（如将搜索半径由 20km 扩至 30km 或扩充“公园/夜市”等通用词），而非过早退化为自由日。

第 2 题 · 拓扑并发与数据隔离边界

LangGraph Send API · 状态隔离 · Channel Reducer
场景设定：在 v3 架构中，系统通过 LangGraph 的 Send("day_node", payload) 动态并发扇出多天行程，最后由 merge_node 汇聚。
  1. 为什么 _fan_out 必须将 city、weather_data、hotel_selected、user_profile 显式打包进 payload，而不是直接从全局 State 读？
  2. 当 N 个 day_node 并行写回结果时，为什么不会发生多线程状态覆盖（Race Condition）？
  3. 多路 day_node 并行汇聚到 merge_node 时，merge_node 会被触发执行几次？
“主要是防止上下文爆炸吧。因为并发节点只需要城市、天气、酒店、画像。Send 机制通过并发多个 agent，每个读初始 payload，根据划分的不同 payload 执行文案，然后通过 reducer 合并。建立全局单例池将叶子任务作为最小单元防止死锁或覆盖。采用 FIFO 队列排队写入。MergeNode 只会触发一次。”
💡 深度评析与代码事实标准答案
  • Send 显式注入的底层原因（builder.py:48-60）： LangGraph 的 Send("day_node", payload) 在底层是物理状态隔离的。子节点 day_node 接收到的 state 仅包含 payload 字典本身，不会继承父图全局 State。若不显式传入共享上下文，子分支内部读不到数据（引发 KeyError）。
  • 并发无覆盖的真实机制（state.py:43, 65）： 非 FIFO 队列，而是依靠 LangGraph 状态通道的 Reducer 声明：plan_days: Annotated[list, operator.add] 与 error_log: Annotated[list, operator.add]。在 Pregel 执行引擎中，同一 Superstep 并行的各个分支产出的字典在步末通过 operator.add（list.extend）进行原子状态规约。
  • merge_node 触发机制： 同一个 _fan_out 派发的 N 个 Send 分支属于同一个执行 Superstep。引擎会等待该步内所有分支执行完毕、完成 Reducer 状态合并后，才一次性推进到下游 merge_node，实测确认只触发 1 次。

第 3 题 · 长期记忆统计信号与异常画像边界

IQR 四分位距 · 众数频率比 · 渐进画像门控
场景设定：用户 Alex 历史上 5 次旅行均为 300~500 元经济酒店、饮食“不吃辣”。第 6 次突然陪客户出差，输入了“价格:1800-2200”与“饮食:爱吃辣”。
  1. 双轨异常检测算法（_compute_outlier_penalty）中，IQR 判定与分类型众数频率比的具体公式是什么？
  2. 该记录是否会写入 SQLite？outlier_penalty 为多少？此时重新计算画像，画像会被突变为豪华型/爱吃辣吗？
  3. 如果 Alex 连续 3 次出差都住 1800 元，记忆系统如何实现平滑真实迁移？为什么设定 trip_count ≥ 5 门控？
“双轨异常检测忘了是哪双轨了，只记得有个方差计算，超出方差就降权。新记录也会写入 SQLite，但是权重降低。由于有缓冲机制，异常情况不会突然改变现行主流画像。如果持续输入豪华型，随着数据增加阈值扩大最终修改。冷启动设定 5 次是因为判定公式需要积累样本才具有统计意义。”
💡 深度评析与代码事实标准答案
  • 双轨异常检测机制：
    1. 数值型（价格/预算/距离）走 IQR（四分位距法，manager.py:252-284）：不用方差是因为均值与方差极易被极端值拉偏；而四分位数与中位数（Median）鲁棒性极高。判定区间为 $[Q_1 - 2\times IQR, Q_3 + 2\times IQR]$。
    2. 分类型（饮食/交通/住宿）走 众数频率比（manager.py:285-330）：新标签历史频次 < 众数频次 × 0.3 时判定为异常。
  • 打标与画像防突变： 异常记录依然写入 SQLite，但打上 outlier_penalty = 0.3（权重打 3 折）。生成画像时取历史价格中位数：5 个 400 元 + 1 个 2000 元的中位数仍为 400 元，Alex 的画像稳定保持为经济型。
  • 真实偏好平滑迁移与冷启动： 随着 1800 元频次增加，frequency_boost 上升，且时间衰减因子（time_decay）赋予最新记录更高权重，价格中位数右移，画像自然平滑过渡。冷启动设定 ≥ 5 次是为了防止单次行为给用户打上永久刻板标签。

第 4 题 · 全图无回环与多层级容灾降级边界

DAG 纯线性拓扑 · 5 级降级链 · 透明交付
场景设定：某次规划同时发生：1) 高德天气接口 10s 超时；2) Day 2 文案 LLM 连续 3 次解析失败；3) merge_node 本地计算总预算超出输入上限。
  1. v3 架构为什么彻底删除了 retry_planner 重试回环？出现校验硬伤系统会怎么做？
  2. 对于天气超时、Day 2 文案失败、Merge 预算硬伤，系统如何逐级兜底降级？最终 status 是什么？
  3. error_log: Annotated[list, add] 如何交付给前端？相比直接抛出 500 报错有何业务价值？
“删除 node 回环本质上是幻觉和时间的考量。在没有回环的情况下，校验硬伤交给后端处理做好标记。天气超时通过限制并发池为 10 排队防触发 QPS，超时后重试或记录日志；Day 2 文案失败会写 error_log，极端情况避免直接报 500。透明降级可以在告知用户没有明确生成的情况下让用户理性参考。”
💡 深度评析与代码事实标准答案
  • 删除回环的决策（ARCHITECTURE.md:95）： v2 方案大模型整单生成 5 天出现硬伤时回环重试，大模型常无法理解硬伤导致连续重试 3 次失败，徒增 15~20s 延迟并崩溃。v3 将分天、路径、选址、预算全量下沉为本地确定性算法，硬伤在结构上物理消灭。偶发硬伤时在 nodes.py:813-815 绝不回环，记录 error_log 直接以 degraded 状态交付。
  • 三处故障的逐级降级流转：
    1. 天气超时：底层 run_mcp 10s 截断，_validate 触发天气兜底提示（“天气数据暂不可用，建议春秋季带外套...”），merge_node 记入 error_log；
    2. Day 2 文案失败：指数退避重试（1s→2s→4s）仍失败后，day_node 立即启用本地静态模板兜底（nodes.py:675-715），基于真实 POI 拼接默认文案，置 status="llm_fallback"，不阻断全图；
    3. Merge 预算超限：校验记录日志，全局 status 标记为 "degraded"。
  • 透明交付业务价值： API 始终返回 HTTP 200 OK + 完整计划 JSON + error_log 列表。前端降级面板按警告级别着色展示，用户拿到 85 分可用方案远好于白屏 500 报错。

第 5 题 · 本地路径求解、BM25 轻量 RAG 与离线测试质量工程

2-opt 消除交叉 · BM25 Query 增强 · 60 个 Fake 单元测试
场景设定：考查本地 TSP 求解算法（贪心+2-opt）、轻量攻略 RAG 检索及 60 个离线单元测试捕获的隐蔽缺陷。
  1. 为什么不直接调高德路径规划 API，而在本地用“Haversine 直线距离 × 1.4 绕路系数”？2-opt 解决了什么问题？时间窗超限如何降级？
  2. 为什么该模块手写轻量 BM25 坚决不上向量库？检索时为何将 Query 增强为“景点名 + 玩法”？
  3. 为什么 60 个单元测试做到无网络全 Fake 注入？捕获的“fan-in 双触发”或“POI 坐标缺失”缺陷具体是如何发生的？
“高德是一对一结构，而我们要多点找自由路径，所以选贪心+2-opt。2-opt 解决时间窗口差的问题，时间超限就把最长耗时任务去除。向量库体型臃肿且语义余弦值计算跟业务关系不大。用景点名+玩法是因为两个维度取并集。聚合双触发缺陷和坐标缺失具体原因忘了。”
💡 深度评析与代码事实标准答案
  • 本地路径求解与 2-opt（route_solver.py:30-75）： 构建 TSP 距离矩阵若调用高德 API 需要 $O(M^2)$ 次请求，数十次外部调用会导致网络延迟从 0.1ms 飙升至数秒并打爆 QPS。采用 Haversine × 1.4 城市绕路系数，0 成本、0.1ms 算出高逼真耗时。2-opt 的核心作用是消除路径自交叉（折返跑）。时间窗超限时绝不删除景点，而是触发软伤降级：保留 POI 顺序但隐去精确时间戳。
  • BM25 攻略 RAG 的 Query 意图词增强（guide_rag.py:121-124）： 攻略段落正文通常不重复出现景点名称（如故宫玩法段落第一句是“从午门进直奔太和殿...”，正文无“故宫”二字）。纯景点名检索会导致大面积词频为零（TF=0）无法召回。将 Query 扩充为 故宫 + 玩法，意图词“玩法”可精准匹配段落标签【玩法】，顺利召回。
  • 离线测试基线捕获的 5 项隐蔽缺陷：
    1. LangGraph fan-in 跨 step 双触发：早期 attraction 与 memory 分支在不同 step 结束时汇聚，导致下游 planner 跑了 2 遍。v3 改为 Send 动态派发同一 step 汇聚修复。
    2. 高德 POI 坐标缺失：高德 text search 返回的 POI 不带 location，进入 K-Means 时全部因缺坐标被丢弃。Wrapper 内部引入 _enrich_pois_with_coords 强制并发调 maps_geo 补齐。
    3. 用户画像 None 击穿：新用户画像缺省字段为 None 引发 KeyError，增加了缺省字典防御。
    4. LLM 幻觉坐标（偏差 1300km）：早期让 LLM 生成经纬度产生巨大偏差，全面改为高德真实数据结构化流转。

🛡️ 第三阶段 · 系统韧性、高并发治理与质量工程深度复盘

1. 全局单例线程池（max_workers=10）与死锁防御

  • 为什么并发量呈乘积形式？ 用户传入 5 个偏好，外层发起 5 路并发周边搜索；每路返回 10 个 POI，内层对 10 个 POI 并发调用 maps_geo 补坐标。瞬间并发峰值达到 $5 \times 10 = 50$ 路！高德免费 Key 上限仅 20~25 QPS，若不限流会瞬间被 429 熔断击穿。
  • 为什么单例池只接叶子任务可防死锁？ 若把外层父任务也提交进池，10 个父任务占满线程池后需要等待子任务执行，但子任务在队列中等待父任务释放线程 → 父等子、子等父，发生经典的线程池饥饿死锁（Thread Starvation Deadlock）。本项目规定全局池只接收原子级 mcp.run 叶子任务，父任务在外部线程运行，彻底消除嵌套依赖。

2. LLM 指数退避（Exponential Backoff）与 Jitter 防惊群

  • 退避时间序列： $\text{Delay} = 1\text{s} \times 2^i + \text{random}(0, 0.5)$ 秒（即第 1 次 $\approx 1\text{s}$，第 2 次 $\approx 2\text{s}$，第 3 次 $\approx 4\text{s}$）。
  • 为什么必须加 Jitter（随机抖动）？ 当 5 个 Day Agent 并发执行遇到网络抖动同时失败时，若无 Jitter，所有 Agent 会在完全相同的第 1.000 秒同时重试，引发惊群效应（Thundering Herd）再度击垮接口；Jitter 将 5 个请求的重试时机随机打散（如 1.08s, 1.23s, 1.45s...），平滑流量尖峰。

3. SSE 客户端断开取消与连接池安全

  • 断连异常捕获： 客户端关闭网页时，ASGI 抛出 asyncio.CancelledError。
  • 后台任务终止： 后端捕获后立即触发 cancel_event.set()，通知后台线程中止后续 LangGraph 节点计算与 Token 浪费。
  • 显式 conn.close()： try...finally: conn.close() 确保即使发生中途断连，每个请求独享的 SQLite 连接也能安全释放，杜绝文件描述符（fd）泄漏。

4. 60 个离线测试捕获的 5 大隐蔽缺陷

  • 测试基线： 基于 FakeAmapWrapper、FakeLLMService 和 FakeRepository，实现 0 网络依赖、0 Token 消耗、0.8 秒全量跑完 60 个用例。
  • LangGraph fan-in 双触发： 早期 memory（1步结束）与 attraction（2步结束）汇聚时，因处于不同 Superstep 导致 planner 节点被重复执行 2 次。v3 改为 Send API 动态扇出与 Reducer 一次性规约彻底根治。
  • 高德 POI 缺坐标： maps_text_search 缺少 location 导致聚类崩溃，测试捕获后在 Wrapper 内增加并发 maps_geo 自动补齐。
  • 画像 None 击穿： 新用户字段为 None 引发 KeyError，增加字典兜底。
  • LLM 坐标幻觉： 编造坐标偏差 1300km，彻底废除 LLM 坐标生成。
